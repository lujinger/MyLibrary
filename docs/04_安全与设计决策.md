
# 04 · 安全与设计决策（v0.1.0）

> 本文是项目的"决策档案"：记录贯穿全模块的关键技术选型、安全策略与踩坑经验。

> 关联文档：[01_需求与范围](./01_需求与范围.md) · [02_数据库设计](./02_数据库设计.md) · [03_API契约](./03_API契约.md)

## 1. 安全设计

### 1.1 认证：JWT（SimpleJWT）

- **决策**：access token 30 分钟 + refresh token 7 天，双 token 机制。

- **理由**：无状态、水平扩展友好；refresh 用于续期，降低 access 泄露窗口。

- **实现**：`MyLibrary/settings.py`（`SIMPLE_JWT`）；签发在 `app/views/auth.py:_get_tokens`。

- **覆盖**：注册/登录 `AllowAny`，其余业务接口 `IsAuthenticated`，未认证统一 `401`。

### 1.2 水平越权防护（IDOR）—— 核心安全策略

- **问题**：用户通过篡改 `book_id`/`library_id`/`record_id` 访问或操作他人数据。

- **决策**：所有按 ID 取资源的查询，**必须把归属条件下推到 SQL 的 WHERE 子句**，而不是先取对象再判 `obj.owner == user`。

- **统一返回**：资源不存在 **或** 不属于本人 → 一律 `404`，绝不返回 `403`。
  - 理由：`403` 会泄露"这个 ID 真实存在但你无权访问"，攻击者可据此枚举有效 ID 进行撞库；`404` 让"不存在"和"无权"不可区分。

- **实现位置**：
  - 同表归属：`get_object_or_404(Book, book_id=..., owner=request.user)`（`views/book.py`）
  - 跨表归属：借阅记录通过书反查主人 → `get_object_or_404(BorrowRecord, record_id=..., book__owner=request.user)`（`views/borrow.py`）
  - 外键赋值时校验来源：`_resolve_library` 带 `owner=request.user`（`views/book.py`），传别人的馆 ID → 404

- **`IsOwner` 权限类**：用于 `BookDetailView`，`obj.owner_id == request.user.pk`。注意：它是**第二道防线**，第一道是查询时的 owner 条件（已保证 404）；两者并存是防御性冗余。

### 1.3 输入校验分层

- **序列化器层**（`serializers/*.py`）：字段类型/长度/必填、`validate_due_date`（归还日不早于今天）、`Library*.validate`（馆重名）。失败 → `400` 字段级错误。

- **视图层业务规则**：借出时 `borrow_status` 必须 available、默认馆不可删、重复归还。失败 → `400 {"detail": ...}`。

- **数据库层兜底**：唯一约束、部分唯一约束。违规 → 应用捕获转 `400`（而非让 500 暴露）。

## 2. 数据一致性

### 2.1 在借唯一性的"双保险"

- **问题**：一本书不能同时被借出两次。单靠应用层校验存在 TOCTOU 竞态（两个并发请求同时通过 `borrow_status==available` 检查）。

- **决策**：应用层友好校验 + 数据库层部分唯一约束兜底。

- **第一层（友好）**：`views/borrow.py` 先查 `book.borrow_status != "available"` → 返回 `400`。

- **第二层（正确）**：`borrow_record` 表上的**部分唯一约束**：
  ```python
  UniqueConstraint(fields=["book"], condition=Q(return_date__isnull=True),
                   name="unique_active_borrow_per_book")
  ```
  并发穿透时由 DB 抛 `IntegrityError`，视图 `except IntegrityError` 捕获，返回同样的 `400` 文案。

- **为什么缺一不可**：只靠应用层 → 并发下数据脏；只靠 DB → 用户看到 500 而非友好提示。

### 2.2 事务原子性

- 借出（建记录 + 改书状态）、归还（写 return_date + 恢复书状态）均包裹在 `transaction.atomic()` 中。

- 保证"记录"与"书的当前态"要么一起成功要么一起回滚，杜绝"记录建了但书状态没改"的不一致。

### 2.3 状态单一数据源 + 冗余当前态

- **单一数据源**：`BorrowRecord.status` 是 `@property`（不落库），由 `return_date` 派生——`return_date` 非空 = returned，否则 = borrowing。杜绝"状态字段"与"日期字段"各自维护导致的不一致。

- **冗余当前态**：`Book.borrow_status` 是冗余字段，为列表/借出校验提供高效过滤（避免每次都关联查在借记录）。

- **同步机制**：两者在同一事务内一起更新（见 2.2）；若极端情况下不一致，以 `return_date` 回算为准（二期可加定时巡检修复）。

## 3. 容器语义与级联

### 3.1 图书馆 = 容器（非收藏夹）

- **决策**：`Book.library` 非空外键，`on_delete=CASCADE`。

- **语义**：书脱离馆没有独立存在意义；删馆 = 删馆内所有书（连带其借阅记录）。

- **对比收藏夹语义**（`SET_NULL`）：书可脱离馆漂流——不符合"个人藏书按馆分组管理"的心智模型，且会产生无主数据。

- **默认馆保护**：注册由 `post_save` 信号自动建默认馆（`is_default=True`），保证用户始终有一个"兜底容器"；默认馆禁删（应用层 400 拦截），新书不传 `library_id` 时自动落入默认馆。

### 3.2 信号的 `raw` 守卫

- `signals.create_default_library` 中判断 `if created and not raw`。

- `raw=True` 出现在 fixtures 加载 / 数据迁移场景，此时不应触发业务副作用（否则加载 fixture 会重复建馆）。这是 Django 信号的标准坑。

## 4. DRF 框架陷阱与规避

### 4.1 `unique_together` 校验器静默跳过

- **坑**：`Library` 有 `unique_together = [["owner", "name"]]`，但 `LibraryCreateSerializer.fields` 只含 `["name", "description"]`，**不含 owner**。

- **DRF 行为**：`UniqueTogetherValidator` 只在**涉及的所有字段都在 serializer fields 中**时才自动生成；缺一个就**静默跳过**，不报错、不警告。

- **后果**：重名馆不被序列化器拦截 → 落到 DB 抛 `IntegrityError` → 接口返回 `500` 而非 `400`。

- **规避**：在 `validate()` 中手动查库查重（`Library.objects.filter(owner=request.user, name=name).exists()`），视图必须传 `context={"request": request}` 让校验器拿到当前用户。更新时用 `exclude(pk=self.instance.pk)` 排除自身。

- **教训**：凡是 `unique_together` 中有字段不在 serializer 白名单里的，必须手动补校验；不能依赖 DRF 自动生成。

### 4.2 双重序列化反模式

- **坑**：包装型序列化器（`{total, page, items}`）的 `items` 若先 `.data`（得到 `list[dict]`）再传给外层，外层会**再序列化一次**。

- **后果**：`BorrowOutSerializer` 的 `book` 是 `PrimaryKeyRelatedField`，二次序列化时拿到的是 `int`（已序列化好的 book_id），调用 `.pk` → `AttributeError: 'int' object has no attribute 'pk'`，列表接口 500。

- **图书模块为何侥幸未炸**：`BookOutSerializer` 无 Relation 字段，二次序列化只是把 dict 当 object 读属性，部分场景不报错——但这是隐患，不是正确写法。

- **规避**：`items` 一律传**原始 queryset 切片**，由外层 serializer 统一序列化一次：
  ```python
  "items": queryset[(page-1)*page_size : page*page_size]
  ```

- **教训**：序列化器只该序列化一次；`.data` 是终点，不该再喂给另一个序列化器。

### 4.3 非 serializer 白名单字段的读取

- `BookCreateSerializer` 不含 `library_id`（由视图注入，不让前端改 owner），但前端需要传。

- **做法**：视图从 `request.data.get('library_id')` 直接读取原始请求数据，自行校验与注入，不依赖序列化器。这是"敏感字段不放白名单 + 视图手动处理"的标准模式。

## 5. 性能策略

| 场景 | 策略 | 位置 |
|---|---|---|
| 列表数据量 | 分页，`page_size` 上限 50 | views/book.py, views/borrow.py |
| 跨表字段序列化 | `select_related("book")` 预加载，防 N+1 | views/borrow.py |
| 馆列表带书数量 | `annotate(book_count=Count("books"))` 一次 SQL，而非逐馆 count | views/library.py |
| 模糊搜索 | `book_name`/`author` 建索引 + `icontains` | models/book.py |
| 列表归属过滤 | owner 条件下推到 WHERE，利用索引 | 全部列表视图 |

> 已知冗余：`Book.book_name`/`author` 同时存在字段级 `db_index=True` 与 `Meta.indexes`，二期收敛为保留其一（见 02 文档第 3 节）。

## 6. 工程规范（项目记忆级）

### 6.1 分层提交规范 ⭐

> 已写入项目记忆，所有后续功能（含二期）统一遵循。

**模型层与接口层必须分开提交**：

- `feat(model): ...` / `fix(model): ...` —— 只含 `models/` + `migrations/` 变更

- `feat(api): ...` / `fix(api): ...` —— 只含 `serializers/` + `views/` + `urls.py` 变更

- `test(...): ...` —— 测试用例

- 理由：模型变更不可逆（影响数据库），接口变更可快速迭代；分开提交让回滚粒度清晰、Code Review 聚焦。

### 6.2 分支与版本

- **Git Flow**：`main`（生产）/ `develop`（集成分支）/ `feature/*`（功能开发）。

- 合并用 `--no-ff` 保留合并节点，形成可追溯的功能拓扑。

- 发版：`develop → main` 合并后打 **annotated tag** `vX.Y.Z`，tag 需单独 `git push origin <tag>`。

- 提交信息：Conventional Commits（`feat:` / `fix:` / `test:` / `docs:` / `merge:`，可带 scope 如 `feat(api)`）。

### 6.3 测试规范

- 框架：Django `APITestCase`；测试数据用 `setUpTestData`（类级事务，每个用例自动回滚，高效隔离）。

- 用例覆盖：正常路径 + 边界 + 错误码 + 安全（IDOR）+ 并发兜底。

- 一期累计 89 个用例全绿（认证 21 + 图书 24 + 图书馆 22 + 借阅 22）。

- **铁律**：测试必须收敛到 0 error。修掉一批 ERROR 后要重跑——被 setUp 级崩溃掩盖的后续错误会在重跑时暴露。

### 6.4 文档模式

- 一期采用**发布归档模式**：功能开发完成、合并后补设计文档（即本 `docs/` 目录）。

- 二期建议切换为**文档驱动**：先写 `03_API契约`（接口契约）→ 评审 → 再开发，契约作为前后端并行与测试的依据。

## 7. 迁移经验

### 7.1 存量表加非空外键的三步范式
给已有数据的 `book` 表加非空 `library` 外键：

1. 模型先加 `null=True, blank=True` → `makemigrations` → `migrate`（此时列可空，不报错）

2. 用 shell 回填存量数据（每本书归到其主人的默认馆），验证 `未归馆的书数量: 0`

3. 模型去掉 `null=True` → `makemigrations` → 对提问选 **2（Ignore for now）** → `migrate`

### 7.2 为什么第三步还会问

- `makemigrations` **只对比模型定义与迁移文件的差异，不查实际数据**。所以 nullable → non-nullable 每次都会提示"impossible to change"。

- 能否安全选 Ignore，取决于**实际数据是否已无 NULL**（已验证为 0）。这是"工具不查数据、人来担保"的典型场景。
